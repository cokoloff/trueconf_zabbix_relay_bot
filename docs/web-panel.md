## Режимы входа

Задаётся переменной `WEBUI_AUTH`:

| Режим | Что доступно |
|---|---|
| `both` | **рекомендуется**: SSO Keycloak + локальный администратор на одной странице входа |
| `keycloak` | только SSO |
| `local` | только локальный администратор |
| `token` | статический `X-WebUI-Token` (для скриптов и healthcheck) |
| `none` | без авторизации (только закрытый контур) |

Страница `/login` показывает кнопку SSO и форму локального входа. Если доступен
только один способ, лишний шаг не создаётся.

## SSO через Keycloak

Вход по OpenID Connect, поток **Authorization Code + PKCE (S256)**.

### Что создать в Keycloak

1. **Client** с именем `tcbot-admin`, тип **public** (Client authentication = Off),
   Standard flow включён, PKCE `S256`.
2. **Valid redirect URIs**: `https://<панель>/auth/callback`
   (плюс `http://localhost:8080/auth/callback` для отладки).
3. **Web origins**: адрес панели или `+`.
4. **Роли** в realm (или в клиенте): `tcbot-admin` — полный доступ,
   `tcbot-viewer` — только просмотр. Назначьте их группам или пользователям.

### Настройка бота

```
WEBUI_AUTH=both
WEBUI_PUBLIC_URL=https://tcbot.example.com
SSO_SERVER_URL=https://auth.example.com
SSO_REALM=your-realm
SSO_CLIENT_ID=tcbot-admin
SSO_ADMIN_ROLES=tcbot-admin
SSO_VIEWER_ROLES=tcbot-viewer
SSO_COOKIE_SECURE=true
SSO_SESSION_SECRET=<длинная случайная строка>
```

`SSO_SESSION_SECRET` лучше задать: без него секрет подписи cookie генерируется
при старте, и после каждого перезапуска нужно входить заново.

### Ошибка `invalid_scope`

Keycloak отвечает так, если запросить scope, не назначенный клиенту:

```
error=invalid_scope&error_description=Invalid scopes: openid profile email roles groups
```

**Про `groups`.** Он не нужен: роли приходят из `realm_access` и
`resource_access` в токене. По умолчанию бот запрашивает
`openid profile email roles` — этого достаточно.

Запрашивайте `groups` только если роли у вас раздаются **группами LDAP**
и имя группы совпадает с именем роли. Тогда:
1. `SSO_SCOPE=openid profile email roles groups`
2. В Keycloak добавьте client scope клиенту:
   *Clients → клиент → Client scopes → Add client scope → groups (Default)*

Бот проверяет scope при входе и **сам исключает недоступные**, запоминая
результат, — поэтому ошибка `invalid_scope` вход не блокирует.

### Если пришло «у учётной записи нет роли»

Вход прошёл, но Keycloak не вернул ролей. Проверьте:

1. **Запрошены ли scope `roles` и `groups`?** Без них Keycloak не кладёт
   `realm_access` / `resource_access` в токен:
   ```
   SSO_SCOPE=openid profile email roles groups
   ```
2. **Назначена ли роль пользователю?** *Users → пользователь → Role mapping
   → Assign role* → `tcbot-admin`.
3. **Добавлены ли client scopes клиенту?** *Clients → клиент → Client scopes*
   → `roles` и `groups` как default.
4. **Совпадают ли имена ролей** с `SSO_ADMIN_ROLES` / `SSO_VIEWER_ROLES`.

Роли читаются из трёх источников — `access_token`, `id_token` и `userinfo`;
поддерживаются `realm_access.roles`, `resource_access.<client>.roles`,
`groups` (берётся последний сегмент пути) и плоский список `roles`.

Если ролей нет вовсе, в лог пишется предупреждение со списком фактически
пришедших claims.

### Проверка токенов

- подпись RS256 по JWKS Keycloak (через `PyJWT[crypto]`);
- `iss`, `aud`, `exp`, `nonce`;
- если `PyJWT` не установлен, подпись не сверяется, но в лог пишется
  предупреждение (проверка claims всё равно выполняется).

Сессия — подписанная HMAC-SHA256 cookie (`HttpOnly`, `SameSite=Lax`, опционально
`Secure`).

## Локальный администратор

Резервный вход, который работает **даже если Keycloak недоступен**.

```
LOCAL_ADMIN_ENABLED=true
LOCAL_ADMIN_USERNAME=local-admin
LOCAL_ADMIN_PASSWORD=            # только для первого запуска
LOCAL_ADMIN_PASSWORD_HASH=       # либо готовый хэш
```

### Первый запуск

1. `LOCAL_ADMIN_PASSWORD=...` — при старте пароль сразу преобразуется в хэш.
2. Ничего не задавать — пароль **генерируется автоматически** и однократно
   записывается в файл `local-admin-initial-password.txt`. После смены пароля
   файл удаляется автоматически.

Получить хэш для `LOCAL_ADMIN_PASSWORD_HASH`:

```bash
python -c "from tcbot.localadmin import hash_password; print(hash_password('пароль'))"
```

**Если заданы оба параметра**, используется `LOCAL_ADMIN_PASSWORD`. Хэш
проверяется на формат: если в `LOCAL_ADMIN_PASSWORD_HASH` по ошибке записан
`client_secret` или обычный пароль, значение игнорируется с ошибкой в логе.

### Хранение и защита

- пароль хранится только как **PBKDF2-HMAC-SHA256** (260 000 итераций,
  случайная соль 16 байт) в `bot_state.json`;
- сравнение постоянного времени;
- **защита от подбора**: 5 неудач по паре (IP, логин) → блокировка 60 с,
  затем 300 и 900 с. Блокировка привязана к IP;
- требования к паролю: минимум 12 символов, буквы и цифры;
- смена пароля — в панели на странице «Локальный вход» или через API.

## Роли

| Роль | Доступ |
|---|---|
| `admin` | полный, включая изменения |
| `viewer` | только чтение (`GET`/`HEAD`/`OPTIONS`) |

Пользователи из `ADMIN_IDS` получают полный доступ автоматически — сравнение
идёт по логину, e-mail и по логину без домена (`admin` = `admin@example.com`).

Все изменения требуют роли администратора: попытка `viewer` выполнить `POST`
возвращает `403`.

## Разделы панели

На главной — только состояние сервиса и логи. Остальное — отдельные страницы
из меню аватара:

| Страница | Назначение |
|---|---|
| `/` | компактное состояние (метрики, heartbeat) и логи |
| `/channels` | каналы: поиск, сортировка, пагинация, редактирование |
| `/channel-stats` | статистика по каждому каналу за период |
| `/outbox` | очередь недоставленных |
| `/send` | ручная отправка сообщения |
| `/settings` | параметры удаления и ограничений |
| `/admins` | администраторы бота |
| `/diagnostics` | данные от SDK: бот, сервер, каналы, чаты, лимиты |
| `/local-admin` | смена пароля локального администратора |

### Графики и календарь

**На главной** — блок «Динамика» с обзорными графиками за период
(6 часов, сутки, 3 суток, неделя). Подробные графики живут на странице
`/channel-stats` — там достаточно места и для 30 каналов.

Над графиками — **плитки с цифрами**: отправлено, отказов, успешность,
средняя задержка, очередь, связь. Раньше очередь и связь рисовались графиками,
но они почти всегда статичны и места занимают много, а информации несут мало.

На главной — обзорные графики:

| График | Что показывает | Тип |
|---|---|---|
| Отправлено и отказы | динамика доставок по часам | линия |
| Задержка доставки | сколько миллисекунд занимает отправка | линия |
| Статусы уведомлений | PROBLEM / RESOLVED и прочие | полосы |
| Очередь | максимальный размер недоставленных | линия |

Графики рисуются на `<canvas>` без внешних библиотек и CDN — наследуют цвета
темы и перерисовываются при изменении размера окна.

Рядом с состоянием — **календарь недели**: столбики по дням, высота
пропорциональна числу уведомлений, цвета — по каналам. Наведение показывает
подсказку с разбивкой по каналам, стрелки листают недели назад и вперёд.

#### Графики на странице статистики

График **«Отправлено по каналам»** и **строгость Zabbix** перенесены на
страницу `/channel-stats`: на главной они не помещаются, когда каналов
больше десяти. Там же — расширенная динамика.

| График | Что показывает | Тип |
|---|---|---|
| **Временная шкала** | точки событий: размер = число сообщений, при наведении видно каналы | точки |
| **Отправлено по каналам** | столбик делится на проблемы (красное) и решения (зелёное); высота — всего; подписи при >16 поворачиваются | столбики |
| Строгость Zabbix | Disaster / High / Average / Warning / Information | полосы |
| Статусы | PROBLEM / RESOLVED | полосы |
| Отправлено и отказы | динамика по часам | линия |
| Задержка доставки | время отправки | линия |

Период переключается тем же селектором, что и у таблицы каналов.

**Временная шкала** — точечный график: каждый интервал — одна точка.
Цвет точки показывает статус:

- **красная** — были проблемы;
- **зелёная** — были решения;
- **красно-зелёная** — в интервале было и то, и другое.

График размечен **горизонтальной сеткой с подписями количества** и
вертикальной сеткой по времени — масштаб виден без наведения.

Размер точки — число сообщений. Наведение показывает подробности:
интервал времени (начало–конец), день недели, сколько было проблем и
решений, разбивку по каналам (для смешанных — «3 / 1») и строгости.
Точки с отказами доставки обведены оранжевым.

**Масштаб шкалы настраивается.** Селектор рядом с заголовком графика:

| Значение | Что означает |
|---|---|
| авто | шаг подбирается под период (около 200 точек) |
| 1 / 5 / 15 / 30 мин | фиксированный шаг |
| 1 / 3 часа | для длинных периодов |

Мелкий шаг на длинном периоде автоматически укрупняется, иначе точек
были бы десятки тысяч и график не отрисовался бы. Точные времена событий хранятся
в файле метрик и переживают перезапуск; для самых старых часов, где точное
время неизвестно, точка ставится на начало часа с пометкой «примерно».

#### Чат по умолчанию

Внизу страницы каналов — блок **«Чат по умолчанию»**: резервный адрес для
уведомлений, пришедших без указания канала.

Кнопка «Изменить» открывает **список чатов, которые уже используются
каналами** — достаточно выбрать нужный и нажать «Сделать основным».
Порядок: текущий чат первым, остальные по алфавиту. В подписи видно, какие
каналы ведут в этот чат.

Если нужно указать чат, не привязанный ни к одному каналу, раскройте
«Ввести chat_id вручную».

- рядом с адресом видно, сколько каналов ведут в тот же чат;
- «Очистить» убирает значение — уведомления без канала начнут отклоняться
  с кодом 400;
- значение сразу сохраняется в файл состояния, перезапуск не нужен.

API: `GET /api/default-chat`, `POST /api/default-chat` с
`{"chat_id": "...", "chat_title": "..."}`.

#### Резервные копии

Страница `/backups` — копии состояния бота (каналы, администраторы,
настройки, история инцидентов).

| Действие | Как |
|---|---|
| Создать копию | кнопка «Создать копию» или автоматически раз в сутки |
| Восстановить | кнопка в строке копии, с подтверждением |
| Удалить | кнопка в строке копии |

Перед восстановлением **текущее состояние сохраняется отдельной копией** —
откатиться можно всегда. В таблице видно, сколько каналов и администраторов
в каждой копии.

Имя файла — `bot_state_ГГГГММДД_ЧЧММСС.json`, как в прежних версиях, поэтому
старые копии остаются совместимыми. Хранятся последние `BACKUP_KEEP` штук.

API: `GET/POST /api/backups`, `POST /api/backups/{name}/restore`,
`DELETE /api/backups/{name}`.

#### Статистика каналов

Страница `/channel-stats` — подробности по каждому каналу за период
(6 часов / сутки / 3 суток / неделя):

| Колонка | Что показывает |
|---|---|
| Канал + мини-график | по часам: красное — проблемы, зелёное — решения; под ним «проблем / решено» |
| Отправлено | успешных доставок |
| Отказы | не доставлено (ушло в очередь) |
| Успех | процент с цветовой полосой: зелёный / жёлтый / красный |
| Ср. задержка | среднее и максимальное время доставки |
| Статусы | разбивка PROBLEM / RESOLVED с подсветкой |
| Последняя | когда канал последний раз получал уведомление |

Сверху — итоги: число каналов, всего отправлено, отказы, общая успешность,
средняя задержка.

Мини-график в столбце «Канал» — сдвоенный: **красная часть столбика — проблемы,
зелёная — решения**. Видно не только объём, но и соотношение: 50/50 — норма,
сплошной красный — канал только сообщает о проблемах, сплошной зелёный —
только о восстановлениях. Под графиком числа «проблем / решено» за период. Есть поиск и сортировка по количеству, имени, отказам,
задержке или времени последней отправки.

API: `GET /api/metrics?kind=channel-report&hours=24`.

Данные копит фоновый сборщик (`METRICS_INTERVAL`, по умолчанию раз в минуту):
снимки состояния дают очередь и связь, а каждая доставка учитывается отдельно —
из неё складываются отправки по каналам, статусы и задержка.

Хранится неделя почасовых точек и год дневной статистики в `bot_metrics.json`.
История **переживает перезапуск**: при старте файл читается, счётчики
продолжаются, а не начинаются заново. Сохранение идёт после каждого снимка
(раз в минуту) и при остановке процесса.

В Docker файл лежит в томе `tcbot-data` (`METRICS_FILE=/app/data/bot_metrics.json`),
поэтому история сохраняется и при пересоздании контейнера.

На работу бота это не влияет: только чтение счётчиков и запись отдельного файла.

### Что показывает диагностика

Страница `/diagnostics` использует методы SDK, которые обычно остаются
незадействованными:

| Что | Метод SDK | Зачем |
|---|---|---|
| ID бота, сервер, версия | `me_id`, `server_name`, `server_version` | понять, кем и куда подключён бот |
| Состояние и порт | `health_check()` | точный статус WebSocket и авторизации |
| Состояние каналов | `get_chat_by_id()`, `get_chat_participants()` | видно, что чат существует, как называется, сколько участников и **состоит ли в нём бот** |
| Чаты бота | `get_chats()` | все чаты с типом и числом непрочитанных |
| Ограничения | `get_file_info_upload_limits()` | максимальный размер файла и запрещённые расширения |

Последнее особенно полезно: канал может вести в удалённый или переименованный
чат, и уведомления будут уходить «в никуда». Диагностика сразу подсвечивает
такие каналы красным и показывает причину.

Проверяются **все каналы**, а не первые N: запросы идут параллельно
(6 одновременно), результаты кэшируются на минуту. Два-три десятка каналов
проверяются за доли секунды. Если проверка не уложилась в отведённое время
(20 секунд по умолчанию), незавершённые помечаются приглушённо — это не ошибка.
Кнопка «Проверить заново» сбрасывает кэш и обходит сервер полностью.

## Эндпоинты

### Настройки инцидентов

В разделе *Настройки* — селектор **«Что делать при восстановлении»**:

- **ничего** — только запись в историю, сообщение о проблеме остаётся;
- **удалить сообщение о проблеме** — чисто в чате, но следов не видно;
- **отправить «восстановлено»** — видно и проблему, и решение;
- **удалить и отправить** — сообщение о проблеме заменяется на «✅ Восстановлено».

**У каждого канала может быть свой режим.** В таблице каналов есть колонка
«При восстановлении»: своя настройка выделена, наследование помечено ↳.
Задаётся в форме редактирования канала (✎). Пустое значение — наследовать
глобальный режим.

Приоритет: **режим канала → глобальный режим**.

Режимы с удалением автоматически включают разрешение на удаление. Порог
`ERROR_DELETE_THRESHOLD_HOURS` ограничивает возраст: старые сообщения
не удаляются, чтобы не пропало то, что давно прочитали.
