## Общая схема

```
Zabbix / Grafana / Alertmanager
            │  POST /webhook?channel=<имя>
            ▼
    ┌───────────────────┐
    │  aiohttp (8080)   │  приём вебхуков, панель, /health, /ready
    └─────────┬─────────┘
              │
         ┌────┴─────┐
         │          │
    доставлено   TrueConf недоступен
         │          │
         │          ▼
         │    ┌──────────────┐
         │    │   Outbox     │  bot_outbox.json (переживает перезапуск)
         │    └──────┬───────┘
         │           │ после восстановления связи
         ▼           ▼
    ┌──────────────────────┐
    │  BotRunner           │  супервизор: пересоздаёт Bot, heartbeat
    └──────────┬───────────┘
               ▼
      TrueConf Server (WebSocket)
```

## Супервизор соединения

`tcbot/runner.py` держит SDK-бота под наблюдением. Зачем это нужно:

библиотека `python-trueconf-bot` умеет переподключаться, но её цикл
соединения завершается окончательно в ряде ситуаций (исчерпаны попытки,
сервер отверг токен, сессия зависла без обрыва TCP). После этого объект `Bot`
уже не восстановит WebSocket, а приложение продолжит работать «вхолостую».

### Что делает супервизор

1. Запускает `bot.run()` и ждёт готовности.
2. Следит за `connected_event` / `authorized_event`.
3. Периодически проверяет связь активным запросом (`heartbeat`).
4. При сбое — пересоздаёт `Bot` целиком и пробует снова.

### Режимы heartbeat

| Режим | Поведение |
|---|---|
| `off` | реагируем только на события SDK |
| `smart` | активная проверка; перезапуск после 3 неудач подряд |
| `strict` | перезапуск сразу после первой неудачной проверки |

Если сервер отвечает **ошибкой API** (а не сетевым сбоем), проверка
автоматически отключается — иначе получались бы ложные перезапуски.

### Пауза между попытками

```
простой < RECONNECT_FAST_WINDOW (10 мин):
    5с → 10с → 20с → 40с → 80с → 160с → 320с
простой ≥ RECONNECT_FAST_WINDOW:
    1800с → 1800с …   (одна попытка в 30 минут)
```

Первые 10 минут бот подхватывает короткие обрывы почти сразу. Дальше — это уже
плановые работы: темп падает до одной попытки в полчаса. После восстановления
связи пауза сбрасывается.

Через `QUIET_AFTER` (10 минут) включается «тихий» режим: в `error.log`
остаётся только первая ошибка, остальное — в `bot.log` и в панели.

## Очередь недоставленных

Системы мониторинга повторяют вебхук несколько раз за десятки секунд и
сдаются. При часовых работах на TrueConf уведомления были бы потеряны —
поэтому `tcbot/outbox.py` сохраняет их на диск.

```
недоставка → POST /webhook → 202 + запись в bot_outbox.json
связь есть  → фоновый flusher отправляет накопленное по порядку
```

| Свойство | Как реализовано |
|---|---|
| Переживает перезапуск | JSON-файл, атомарная запись (tmp + replace) |
| Порядок | FIFO |
| Дубликаты | окно дедупликации `OUTBOX_DEDUP_WINDOW` |
| Схлопывание | по одному триггеру остаётся последнее состояние |
| Ограничения | `OUTBOX_MAX_SIZE` сообщений, `OUTBOX_TTL_HOURS` часов |

При переполнении вытесняется старейшее сообщение; счётчик потерь виден
в панели.

## Защита от дублей доставки

Симптом: после перезапуска сервиса в чат приходят сообщения, которые там уже были.

**Основная причина — код ответа 500 после успешной доставки.**

Обработчик вебхука отправлял сообщение в чат, а затем учитывал метрику
доставки. Если учёт падал (например, `KeyError: 'latency_sum'` при чтении
файла метрик, записанного более ранней версией бота), исключение уходило
во внешний `except` и вебхук отвечал **500**. Zabbix считал доставку
неуспешной и повторял запрос — в чат уходила копия. Так как повторов было
до трёх, одно уведомление появлялось 2–4 раза.

Дополнительный фактор — таймаут отправки: `send_message` уходит на сервер,
но подтверждение не приходит вовремя, бот считает доставку неуспешной и
кладёт сообщение в очередь, **хотя в чате оно уже есть**; при следующем
перезапуске `flush_outbox` отправляет его снова.

Исправления:

- **после успешной доставки ответ всегда 200** — любая ошибка учёта метрик
  или истории инцидентов логируется, но не меняет код ответа;
- бакеты файла метрик **нормализуются** при чтении: недостающие поля
  дополняются, поэтому старый файл не роняет обработчик;
- реестр доставленного не даёт отправить то же сообщение повторно.

Решение — реестр доставленного (`bot_delivered.json`). Ключ — хеш от
пары «чат + текст», окно защиты `DELIVERED_DEDUP_WINDOW` (15 минут):

- перед отправкой проверяется, не уходило ли это сообщение недавно;
- после успешной отправки отметка записывается;
- `flush_outbox` пропускает то, что уже доставлено другим путём;
- реестр **хранится на диске**, иначе после перезапуска он пуст —
  а именно на рестарте дубли и появляются.

## Определение статуса уведомления

Zabbix с шаблоном сообщения часто **не передаёт поле `status`** — состояние
закодировано в самой теме: «❌ Проблема …» или «✅ Решено …». Раньше такие
уведомления попадали в метрики без статуса, и разбивка на графике оставалась
пустой.

Бот определяет статус по тексту, если поле не пришло (`guess_status`):
ищет признаки в начале сообщения — «проблема», «авария», «firing» для
PROBLEM; «решено», «восстановлено», «resolved» для RESOLVED. Явно переданное
поле `status` всегда имеет приоритет.

Это влияет не только на графики: от статуса зависит история инцидентов
(удаление сообщения о проблеме после восстановления).

### Строгость

Zabbix передаёт серьёзность отдельной строкой в тексте:
`Строгость: Average ⚡`. Это **не** то же самое, что статус: проблема может
быть `Information`, а может быть `Disaster`.

`guess_severity` распознаёт пять уровней — Disaster 💀, High 🔥,
Average ⚡, Warning ⚠️, Information ℹ️ — и приводит к каноническому
названию. Строгость копится отдельно от статуса и показывается на главной
своими цветами (от тёмно-красного для Disaster до синего для Information).

`FIRING` — признак Grafana/Alertmanager, а не Zabbix: у Grafana статус
приходит отдельным полем, и строгости в тексте нет.

## Инциденты: что происходит при восстановлении

Бот помнит отправленные проблемы и по-разному реагирует на их решение.
Режим переключается в панели (*Настройки → «Что делать при восстановлении»*):

| Режим | Действие |
|---|---|
| `notify` | только записать в историю, сообщение остаётся |
| `delete` | удалить сообщение о проблеме |
| `resolve` | отправить «✅ Восстановлено» |
| `both` | удалить и отправить «✅ Восстановлено» |

### Режим для отдельного канала

У каждого канала может быть **своя** настройка. Логика приоритета:

    режим канала (если задан) → иначе глобальный режим

Пустое значение в канале означает «наследовать глобальный». Так можно,
например, в канале `network` удалять сообщения, а в `audit` — присылать
«восстановлено», не меняя общее поведение.

Задаётся в панели: *Каналы → ✎ у нужного канала → «При восстановлении»*.
В таблице видно, у кого своя настройка (выделено), а у кого наследование
(со значком ↳).

### Как находится инцидент

Ключ инцидента должен совпадать у PROBLEM и RESOLVED, иначе сообщение
не найти. Раньше ключом был хеш от «хост + тема + текст», а Zabbix
присылает разные тексты при проблеме и решении — ключи не совпадали,
и ничего не удалялось.

Теперь ключ строится по убыванию надёжности:

1. `triggerid` — один на весь инцидент (лучший вариант);
2. имя триггера (`triggername`, `alertname`);
3. тема без меток статуса: «❌ Проблема X» и «✅ Решено X» → «X»;
4. текст без меток статуса.

`eventid` **не подходит**: у проблемы и восстановления это разные события.

### Повторные PROBLEM

Zabbix повторяет одно и то же уведомление, пока проблема не решена —
каждое повторение создаёт **новое сообщение в чате**. Раньше запись
инцидента перезаписывалась, сохранялся только последний `message_id`,
и при решении удалялось одно сообщение из нескольких.

Теперь инцидент копит **все** идентификаторы (`message_ids`) и счётчик
повторов (`repeat_count`). При решении удаляются все сообщения проблемы.

Запись об инциденте **сохраняется на диск сразу** при получении проблемы,
а не ждёт планового автосохранения (раз в минуту). Иначе при аварийной
остановке (`kill -9`, OOM) запись терялась бы вместе с `message_id`, и
удалить сообщения при восстановлении было бы невозможно.

### Идентификатор сообщения

Чтобы удалить сообщение, нужен `message_id`. Он берётся из ответа
`send_message` и сохраняется вместе с инцидентом. Если проблемы приходили
до обновления бота (или доставлены из очереди), идентификатора нет —
такие сообщения не удаляются, в журнал пишется предупреждение.

## Разметка сообщений

TrueConf Server разбирает разметку не так, как ожидается. Проверено на 5.5.8:

| Что делаем | Что было бы иначе |
|---|---|
| не используем обратные кавычки | MARKDOWN превращает их в `<code lang="pre">`, клиент этот тег не понимает |
| экранируем `<` и `>` | сырое `<id>` сервер считает тегом и выбрасывает |
| маркер списка `•` вместо `-` | строка с дефиса в MARKDOWN склеивается с соседней |
| перенос строки — `<br>` | сырой перевод строки в HTML не даёт переноса |
| структурированные сообщения — `ParseMode.HTML` | MARKDOWN теряет часть форматирования |

Всё это инкапсулировано в `tcbot/markup.py`: `MessageBuilder` экранирует любое
внешнее значение и отдаёт готовый HTML. Текст уведомлений проходит через
`safe_text()`.

Дополнительно `normalize_command_text()` очищает входящие команды от невидимых
символов: клиенты могут прислать `/channels&nbsp;2` или вставить zero-width
пробел, из-за чего команда перестаёт распознаваться.

## Логирование

| Файл | Содержимое |
|---|---|
| `bot.log` | всё, уровень DEBUG |
| `chat.log` | входящие сообщения и команды |
| `webhook.log` | приём вебхуков |
| `error.log` | ошибки отправки и сбои связи |
| `delete.log` | удаление сообщений |
| `error_history.log` | история инцидентов |

Ротация: 50 МБ × 10 файлов. Собственные обработчики библиотеки `trueconf`
отключаются при старте, поэтому каждое событие попадает в лог одной строкой.
